# Special case：管理员协助配置 Telegram

此方案保留在 **main 的 Docker 服务**中。管理员初始化、用户资料管理与审计已实现，用户自助 App 配置与测试 Bot 数字 ID 白名单已实现；管理员协助配置、资源分配和频道审批仍为待实现设计；不适用于 `feature-cfworker`。现有接口和环境变量以主 [README](../README.md) 为准。

## 设计理念

平台注册与 Telegram 配置分开，用户可以先取得平台身份，再选择自行配置或管理员协助。普通流程使用用户自有 Telegram 资源；无法自行配置的用户作为 special case，由管理员明确启用。

管理功能放在现有 Node.js API 服务内，与业务接口共用 Docker 镜像、MySQL/PostgreSQL 和 Redis，通过角色与资源归属控制权限。管理员身份管理和资源分配分别设计，资源分配计划采用一个业务用户一个 Bot，保持当前 Landing Page 模型。

白名单采用基础规则，Bot 检查发送者，私有 Channel 按名单审批。平台持有的凭据仍由平台保管，业务授权与 Telegram 个人账号登录态分别管理。主 README 明确列出当前能力与待实现项，保留方案中的变量和接口在实际实现前不作为部署说明。

## 使用流程

普通用户完成邮箱注册后，自行提供 Telegram App `api_id`、`api_hash`，登录个人 Telegram 账号，再创建自己的 Bot 和 Channel。

对暂不提供 Telegram 配置的用户保留 special case：

1. 用户正常完成邮箱注册，暂时跳过 Telegram 配置。
2. 用户随后自行补充 App 凭据，或者由管理员协助补充。登录 Telegram 仍需账号本人提供验证码及必要的两步验证密码。
3. 用户无法自行配置时，管理员可以将平台管理的 Bot、Channel 分配给该用户。
4. 分配的 Bot 使用简单白名单限制响应；Channel 使用私有频道及入群审批限制访问。

邮箱注册与 Telegram 登录是两个步骤，当前已经可以先注册、后登录 Telegram。待增加的是配置管理、管理员协助分配和白名单，不需要在注册时强制提交 Telegram 凭据。

`api_id/api_hash` 是 Telegram App 凭据，Bot Token 是 Bot API 凭据。提供已有 Bot Token 与登录个人账号创建新 Bot 是不同操作；Bot Token 不能代替个人账号登录来创建 Channel。

## 管理员与默认资源

现有 API 服务已增加管理员账号与权限校验，普通注册不能选择管理员角色。管理员可修改普通用户的邮箱、密码和启停状态，操作持久化审计。用户自助 App 配置与双 Bot 项目流程已实现；管理员替用户配置、special case 开关与资源分配仍待实现。

首次管理员账号和密码通过以下**容器运行时环境变量**指定，沿用平台的邮箱账号体系：

| 必填运行时变量 | 用途 |
| --- | --- |
| `ADMIN_EMAIL` | 首次创建的管理员登录邮箱，不设默认账号 |
| `ADMIN_PASSWORD` | 首次创建的管理员密码，沿用平台密码规则（12–128 字符），不设默认密码 |

配置示例：

```dotenv
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=REPLACE_WITH_A_RANDOM_PASSWORD
```

两个变量必须同时填写，缺失或格式不符合要求时启动报错。首次启动直接将管理员邮箱、密码哈希及角色保存到数据库，无需邮箱验证；密码不明文入库、不写日志，也不进入镜像构建参数。管理员通过 `POST /admin/login` 提交账号密码直接登录，Redis 会话默认 2 小时，无需 SMTP；普通用户仍走邮件验证码。

初始化应幂等：已有管理员账号时，重启或修改上述变量不覆盖其密码与已修改的设置；后续改密走账号改密流程。更换 ADMIN_EMAIL 不迁移或删除旧账号；新邮箱不存在时会新增管理员。管理员邮箱与已有普通用户冲突时停止初始化并明确报错，不能自动提升权限。`ADMIN_API_KEY` 是现有管理员接口的独立凭据，与管理员账号密码不同。

上述变量已接入服务、`.env.example` 和 Compose。管理接口拒绝修改管理员账号、角色、用户 ID、Telegram 登录态和资源归属；管理员自身改密使用 `/auth/password`。成功资料修改与审计写入同一事务，修改会撤销目标用户旧会话。审计记录时间、IP、连接来源 IP、UA、操作者、目标用户、结果及脱敏变更，不记录密码或 Token。

管理员接口同时采用 Redis IP 防爆破，默认同 IP 一小时内累计两次认证失败后封禁 3600 秒。正确凭据不能绕过已有封禁；失败与封禁请求仍审计，业务参数错误不计数。规则通过运行时 ADMIN_AUTH_MAX_FAILURES、ADMIN_IP_BAN_SECONDS 配置，默认 2/3600。

special case 默认关闭，由管理员启用。默认 Bot 信息初始化指登记并验证平台已有 Bot，不代表启动服务时自动创建 Telegram 账号或 Bot。App 凭据、个人账号登录态和 Bot Token 分别管理，敏感信息沿用当前加密存储。

为保持当前一个 Bot 对应一套 Landing Page 配置的结构，special case 优先采用**每个业务用户每个环境分配独立 Bot**。管理员可以统一持有这些 Bot，但不能把同一个 Bot 当作多个用户各自独立的 Bot；同一个 Bot 的 Webhook 和卡片配置会互相影响。多用户共用一个 Bot 并分别配置 Landing Page，需要另行设计路由与授权。

平台管理的 Bot Token 和 Telegram 个人账号登录态不能直接复制给被分配用户。用户只获得被分配资源的业务操作权限；普通用户不能修改平台资源的 Token、归属或全局 Webhook。

## 简单白名单

白名单按 Bot、Channel 分别配置，由管理员或获授权的资源用户维护。开启限制后，空白名单默认拒绝访问。

Bot 基础授权使用 Telegram 更新中发送者的数字用户 ID；username 仅用于展示和人工核对。测试 Bot 已实现此规则，special case 白名单管理仍待实现。不能使用请求者自行填写的 username 作为身份依据。

白名单限制的是 Bot 的响应，不能阻止其他人搜索或打开 Bot 对话。名单应明确填写允许访问的 Telegram 用户；仅填写平台账号持有人会使其他访客无法收到 Landing Page 卡片。

Channel 保持私有，使用需要管理员批准的邀请链接，按白名单审批；初期可由管理员人工完成。仅在 API 中检查白名单不能限制 Telegram 内的频道访问。更换名单后，已有成员和旧邀请链接需要单独处理；公开频道不适用于此访问限制。

## 当前支持与待实现内容

| 项目 | 当前 main | 保留方案 |
| --- | --- | --- |
| 邮箱注册后延后登录 Telegram | 已支持 | 保持现有分步流程 |
| 用户保存与修改自己的 App 凭据 | 已支持 | 管理员协助仍待实现 |
| 管理员认证 | env 直接创建、账号密码直接登录、角色校验；可选 `ADMIN_API_KEY` | 保持与资源分配权限分别管理 |
| 用户资料管理与审计 | 已支持查询、修改邮箱/密码/启停状态、持久化审计 | 后续扩展 Telegram 配置管理 |
| Telegram 默认配置 | API 使用用户 App，TG_API_ID/TG_API_HASH 仅独立脚本 | 与 special case 的启停、资源分配分别管理 |
| 平台 Bot、Channel 登记及分配 | 未实现 | 验证资源后分配给指定用户 |
| Bot 白名单 | 测试 Bot 已按数字 ID 检查，special case 未实现 | 使用稳定数字 ID 管理授权 |
| Channel 白名单 | 未实现 | 私有频道、审批邀请及名单核对 |

现有 `TG_API_ID/TG_API_HASH` 默认值不等于共用 Bot，也不是管理员控制的 special case 开关。当前不要据此开放受白名单保护的平台 Bot。

实现时需同步提供 MySQL/PostgreSQL 数据结构升级、管理员与普通用户权限检查、资源归属校验、加密持久化、API 示例和运行时配置说明，并验证越权、空名单、未匹配用户及重启后的配置行为。完成前，主 README 的 API 清单不列出这些接口。

## 当前统一流程

普通用户统一使用[项目开通流程](PRODUCT-FLOW.md)：注册、登录、保存自有 App、认证 Telegram，系统创建测试/生产独立资源。每个环境资源独占，测试白名单按 Telegram 数字 ID 判断；username 不作为身份主键。上述 special case 平台资源分配和频道审批仍为方案，不是当前可调用接口。
